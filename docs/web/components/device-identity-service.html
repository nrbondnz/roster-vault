DeviceIdentityService

Trust Anchor 2 — one ECDSA P-256 keypair per physical device, generated once, on first run.

Type
Dart service, via the biometric_signature plugin
Defined in
lib/services/device_identity_service.dart
Key alias
roster_vault_device_key, requireAuthentication: false

Hardware-backed via Android Keystore/StrongBox or iOS Secure Enclave. requireAuthentication: false is deliberate — this key isn't gated by a person's local factor, only by the hardware itself; Trust Anchor 3 (UserIdentityService) is the per-person, PIN/biometric-gated credential. The plugin's createKeys silently replaces an existing key under the same alias unless checked for first — every call site here checks getKeyInfo before ever calling createKeys, so a routine app relaunch can't rotate the device key out from under an already-issued token.

A real, fully-diagnosed bug, not a plugin defect: on real Android hardware this failed with BiometricError.unknown "Foreground activity required" even though the app was confirmed fully foregrounded and drawn. Root cause: the plugin requires MainActivity to extend FlutterFragmentActivity, not Flutter's template-default FlutterActivity — documented in the plugin's own README, just never applied in this project's original scaffolding. Fixed; confirmed working with a real Device ID and a genuinely short EC/P-256-shaped public key (not the long RSA-2048 SPKI this plugin falls back to on Windows, a dev-convenience platform only).

See Platform Differences for the iOS side of this same key-generation path — reasoned from the plugin's actual Swift source, not yet verified on real hardware.
