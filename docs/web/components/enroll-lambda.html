enroll Lambda

The resolver behind the enroll mutation — writes the enrollment record and asks KMS to sign the offline capability token.

Type
AppSync direct Lambda resolver, Node.js
Defined in
amplify/functions/enroll/handler.ts
Grants
exactly dynamodb:GetItem, dynamodb:PutItem, kms:Sign — nothing broader

Reads any existing DeviceEnrollments row first to preserve epoch across re-enrollment — only an explicit admin action (Task 8) ever bumps it, never a person's own re-enroll. Writes {deviceId, userId, devicePubKey, userPubKey, epoch, status, lastIssuedExpiry}, then hand-builds a standard ES256 JWS ({user_id, device_id, scopes: [offline_signin], epoch, iat, exp} at ~48h TTL) signed via kms:Sign.

KMS returns the signature DER-encoded; JWS ES256 (RFC 7518 §3.4) needs the fixed-width raw R‖S concatenation instead — the one non-obvious wire-format conversion in the whole handler, and the same one UserIdentityService.signChallenge later has to do again for the device-side challenge-response signature, once real Android hardware made checking the plugin's own output format possible.

Self-reviewed for IAM scope creep: the initial implementation used grantReadWriteData(), granting Query/Scan/DeleteItem/batch operations the handler never calls — tightened to exactly the two actions it actually uses.
