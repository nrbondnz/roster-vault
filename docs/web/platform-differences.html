Platform Differences

Windows, Android, and iOS diverge in exactly three places: how the hardware-backed device key actually gets created, what format its signatures come back in, and what "delete the app" actually clears. Everything else — enrollment, offline verification, the PIN-wraps-token design — is platform-agnostic and unchanged.

Read the status badges carefully. Verified means observed on real hardware this session. Reasoned from source means the plugin's actual Swift/Kotlin implementation was read directly and the conclusion follows from that reading — stronger than a guess, but explicitly not the bar this project has held everywhere else, which is proof on the device. The Android row cleared both stages: it looked correct on a first read of the source too, and was still wrong until it was actually run — see DeviceIdentityService. A Mac is now available; iOS build tooling (Xcode 26.6, CocoaPods 1.16.2, `pod install`) is verified working, and the on-device rows below are in progress this session. Nothing on the iOS side has cleared the second bar (real-device proof) yet.

Signature format

Both platforms that actually produce ECDSA P-256 encode the signature the same way — DER (ASN.1 SEQUENCE{INTEGER r, INTEGER s}).

AndroidiOS
API called Signature.getInstance("SHA256withECDSA") — standard JCA, always DER SecKeyCreateSignature(_, .ecdsaSignatureMessageX962SHA256, _) — X9.62, also DER
Consequence The DER-to-raw conversion in UserIdentityService (mirroring the same fix already needed for KMS's own DER output in amplify/functions/enroll/handler.ts) is shared, platform-agnostic Dart — not Android-specific code that needs an iOS equivalent written.
Status Verified real device-to-token round trip Reasoned from source not yet exercised against a real signature

If this turns out wrong on real iOS hardware, it fails loudly (a signature verification failure) — there's no silent partial-success case.

Local storage persistence on uninstall

The one difference with an actual behavioral consequence beyond "which crypto backend."

AndroidiOS
What "delete the app" clears Everything — flutter_secure_storage and any EncryptedPartitionStore files are app-scoped, wiped by the OS on uninstall Nothing. iOS Keychain items survive app deletion by design (Apple's own documented behavior)
Why it matters here Matches the project's implicit assumption throughout This project's entire premise is a shared, unmanaged device with no MDM — without a fix, deleting and reinstalling on an iPhone would silently keep the old device key, every enrolled token, and every PIN-wrapped partition key from before the reinstall
Fix None needed lib/services/fresh_install_guard.dart (FreshInstallGuard) — called first in main(). Detects a fresh install via a marker file in the app support directory (which is removed on iOS uninstall, unlike Keychain) and wipes stale data when the marker is absent but old data is present
Status N/A no fix needed Unit-tested 4 cases, real temp dir + in-memory storage fake — not yet run against the real Keychain or a real install/delete/reinstall cycle

What's genuinely unchanged

Worth stating explicitly so the differences above don't read as bigger than they are — everything downstream of key generation is identical code, no platform branches: Enrollment (the same enroll mutation, same Lambda, same KMS signing, regardless of which platform's key made the request), Offline Sign-In (OfflineVerifier is pure Dart, no platform import at all), and the PIN-wraps-token design in Encrypted Storage (PinService, PartitionKeyService, and DeviceMasterKeyService are all pure Dart; sqlite3mc is selected via the same pubspec.yaml hook on every platform — though whether that precompiled binary genuinely ships for iOS the same way it does for Android/Windows hasn't been independently confirmed).
