Call Tree & Glossary

Two different things, kept deliberately separate. Cognito (a component) performs SRP sign-in (a function of that component) — that's a parent→child relationship, the call tree below. But SRP itself is a concept with meaning independent of Cognito, the same way ECDSA and DER encoding are concepts independent of KMS or biometric_signature — several different components' functions rely on the exact same underlying concept, so it gets exactly one definition, not one copy per component. That's the glossary, the second section below.

Every function name in the tree is sourced from the actual current code — read directly while building this page, not paraphrased from the diagrams elsewhere on this site. Where a function relies on a standalone concept, its name links down into the glossary; every glossary entry links back up to everywhere in the tree that relies on it.

Call Tree — components and their real functions

  • RosterScreen the app's real entry point
    • RosterRegistryService.listProfiles() — on-device only, no network call
    • RootDetectionService.isLikelyCompromised() — checked once per screen lifetime (initState); a filesystem-existence check against well-known root/jailbreak artefact paths, best-effort by design — changes what the UI shows, never what it allows, since this device class is deliberately unmanaged
    • PinLockoutService.lockedUntil(userId) — checked before showing the PIN dialog at all, so a locked-out profile can't burn CPU on Argon2id or learn anything from further attempts
    • LocalUnlockService.unlock(userId, pin) — see LocalUnlockService below for what this actually does
    • "Add a person" → pushes AuthGate (the one online-only surface; greyed out when connectivity_plus reports no network)
  • ProfileHomeScreen where a selected profile actually lands (same file as RosterScreen)
    • ClockIntegrityService.isClockRolledBack() — checked before the offline verification below even runs; a rolled-back clock is refused with its own named reason rather than silently passing the ordinary expiry check
    • OfflineVerifier.verify() — see OfflineVerifier below for its five checks in full; on success, feeds the token's own iat claim to ClockIntegrityService.recordObservedServerTime(), raising the stored high-water mark used by the rolled-back-clock check above
    • EnrollmentService.enroll() — Task 8's "Refresh now": calls the same AppSync enroll mutation again while online; a revoked profile is refused without touching the already-verified local session
  • LocalUnlockService the PIN gate
    • isSetUp(userId) — does a partition file already exist for this person on this device
    • setUpPin(userId, pin, token)
      • PartitionKeyService.deriveUserPartitionKey() — HKDF, deterministic from K_device + userId, no PIN involved
      • PinService.wrap(pin, token) — Argon2id-derived key, AES-GCM encrypt
    • unlock(userId, pin)
      • EncryptedPartitionStore.open() — see below
      • PinService.unwrap(pin, wrapped) — AES-GCM decrypt; wrong PIN returns null, never throws
  • EncryptedPartitionStore sqlite3mc-ciphered SQLite, one file per person
    • open(dbPath, partitionKey) — PRAGMA key against the sqlite3mc cipher build
    • wrong-key rejection — proven by actually reading a real row back, not just by PRAGMA key not throwing
  • OfflineVerifier zero network calls, enforced by construction — no http/Amplify import in the file at all
    • signature check — JWS (ES256) verify against the baked-in issuer public key
    • expiry check — the token's exp claim against the device clock
    • device-id check — the token's device_id claim against this device's own id
    • epoch check — against the locally-persisted known epoch, deliberately not the token's own epoch claim (that would make the check a tautology)
    • challenge-response — proves possession of the private key, not just the token blob
      • UserIdentityService.signChallenge(userId, nonce) — see below
      • verifies the echoed nonce matches, as another JWS
  • DeviceIdentityService Trust Anchor 2 — one keypair per device
    • getKeyInfo() — checked first, every time; the plugin's createKeys silently replaces an existing key under the same alias otherwise
    • createKeys(signatureType: ecdsa) — ECDSA P-256, hardware-backed via Secure Enclave / Android Keystore
  • UserIdentityService Trust Anchor 3 — one keypair per enrolled person
    • ensureUserKeyPair(userId) — same get-then-create pattern as DeviceIdentityService, a per-user key alias
    • signChallenge(userId, nonce)
      • createSignature() — produces an ECDSA signature, DER-encoded
      • DER-to-raw conversion — the exact same fix already needed for KMS's own DER output, ported rather than reinvented
      • assembles the result as a JWS
  • Cognito User Pool the one moment this app is online by design
    • SRP sign-in — the real protocol behind Amplify.Auth.signIn, not a plaintext password round trip
    • session/ID token issuance — Cognito's own JWTs, distinct from this project's ES256 offline-capability tokens (see the enroll Lambda below)
  • AppSync — enroll mutation Cognito User Pool-authorized, resolved by a direct Lambda resolver
    • verifies the caller's ID token before the Lambda below ever runs — ctx.identity.sub is already a verified claim by the time the handler sees it
  • enroll Lambda amplify/functions/enroll/handler.ts
    • GetItemCommand — reads any existing DeviceEnrollments row: preserves the epoch across re-enrollment, and refuses outright if status === 'revoked' (Task 8)
    • kms:Sign — see KMS issuer key below
    • DER-to-raw conversion — the same wire-format fix UserIdentityService needed independently, for the same reason
    • PutItemCommand — writes the row (deviceId, userId, both public keys, epoch, status, lastIssuedExpiry)
    • hand-builds the final token as a JWS (ES256)
  • KMS issuer key ECC_NIST_P256, SIGN_VERIFY only
    • kms:Sign (ECDSA_SHA_256) — see ECDSA and DER; KMS returns DER, the Lambda converts it
    • kms:GetPublicKey — the only way the public half ever leaves KMS; the private key never does, by construction (an AWS KMS asymmetric CMK)
  • DeviceEnrollments (DynamoDB) PK deviceId, SK userId
    • read/written only by the enroll Lambda above — no other component touches this table directly

Glossary — standalone concepts

Each of these has a real meaning outside this project entirely. Every entry links back to everywhere in the tree above that actually relies on it — the point of separating concept from component in the first place.

SRP — Secure Remote Password

A password-authenticated key-exchange protocol. Proves both sides know the password without the password (or anything equivalent to it) ever crossing the network in either direction — the client and server each derive a shared session key from the password independently, and the protocol proves the derivation matched. This is what Amplify's Auth.signIn actually runs under the hood against a Cognito User Pool; it is not a plaintext password POST.

Used by: Cognito User Pool → SRP sign-in

ECDSA (P-256)

Elliptic Curve Digital Signature Algorithm — an asymmetric signature scheme. A private key signs a message; anyone holding the corresponding public key can verify the signature without ever being able to forge one or recover the private key from it. P-256 (secp256r1 / prime256v1) is the specific curve this project uses everywhere it signs anything, chosen consistently across all three trust anchors.

Used by: KMS issuer key (kms:Sign) · DeviceIdentityService (createKeys) · UserIdentityService (createSignature)

DER encoding

Distinguished Encoding Rules — a specific, deterministic byte encoding for ASN.1 structures. An ECDSA signature is mathematically just two integers, r and s; DER wraps them as SEQUENCE { INTEGER r, INTEGER s }, a variable-length format. Both this project's KMS calls and its on-device biometric_signature calls return signatures DER-encoded — confirmed by reading each platform's actual signing API, not assumed — while JWS (below) needs a fixed-width raw concatenation instead, which is why the same conversion function had to be written twice, once in TypeScript for the Lambda and once in Dart for the device.

Used by: enroll Lambda's DER-to-raw conversion (KMS's output) · UserIdentityService.signChallenge's DER-to-raw conversion (the device key's output)

JWS / JWT (ES256)

JSON Web Signature — a compact, signed token format: base64url(header) . base64url(payload) . base64url(signature). A JWT is the specific case where the payload is a JSON claims set, which is what every token in this project actually is. ES256 names the algorithm in the header — ECDSA with P-256 and SHA-256 — and mandates the raw, fixed-width 64-byte signature format (not DER), the exact conversion the DER entry above describes.

Used by: the enroll Lambda's issued token · OfflineVerifier's signature check and challenge-response verification · UserIdentityService.signChallenge's assembled response

Argon2id

A memory-hard key-derivation function purpose-built for low-entropy secrets like PINs and passwords — winner of the 2015 Password Hashing Competition. Deliberately slow and memory-expensive to compute, which is exactly what makes brute-forcing a 4-digit PIN impractical even with GPU/ASIC hardware, unlike a fast general-purpose hash. This project never stores a PIN hash to compare against; Argon2id output is used directly as an AES-GCM key, so correctness is proven by whether decryption succeeds, not by a comparison.

Used by: PinService.wrap / unwrap, called from LocalUnlockService

HKDF

HMAC-based Key Derivation Function (RFC 5869) — expands one high-entropy secret into one or more independent-looking derived keys, each tied to a distinct "info" parameter. Here, one device-wide secret (K_device) plus a person's userId as the info parameter deterministically derives that person's own partition key (K_user) — same inputs always produce the same key, and different userIds produce unrelated keys, without needing to separately store a key per person.

Used by: PartitionKeyService.deriveUserPartitionKey, called from LocalUnlockService

AES-GCM

AES in Galois/Counter Mode — an authenticated encryption cipher: it encrypts and produces a MAC in one pass, so decryption with the wrong key doesn't silently produce garbage, it fails loudly and verifiably. That authentication failure is exactly how a wrong PIN gets detected in this project — there's no separate correctness check, the cipher's own integrity check is the check.

Used by: PinService.wrap / unwrap, called from LocalUnlockService

Secure Enclave / Android Keystore

Hardware-isolated key storage, one per mobile platform. A private key generated inside either can be used to sign or decrypt, but the raw key material itself is architecturally incapable of ever leaving the secure hardware — not "the API doesn't expose it," the hardware itself has no path out. This is what makes Trust Anchor 2 and 3's "private key never touches app memory" claim a hardware guarantee, not a software promise.

Used by: DeviceIdentityService · UserIdentityService · see also Platform Differences for exactly how the Android Keystore and iOS Secure Enclave paths diverge

AWS KMS asymmetric CMK

A Customer Master Key in AWS Key Management Service, configured for asymmetric sign/verify rather than symmetric encrypt/decrypt. AWS holds the private key material inside its own HSM infrastructure; every use is an API call (kms:Sign) that never returns the key itself, only a signature — the cloud-side equivalent of the Secure Enclave/Keystore guarantee above, for the one key that has to live on the server instead of a device.

Used by: the KMS issuer key (Trust Anchor 1)

Not glossary-worthy — on purpose

Several real functions in the tree above are deliberately not given their own glossary entry — "wrong-key rejection," "greyed out when offline," "preserves the epoch across re-enrollment" are all real project behavior, but they don't mean anything outside this codebase the way SRP or ECDSA do. A glossary entry for project-specific behavior would just be a second, worse copy of the component page it belongs to.
